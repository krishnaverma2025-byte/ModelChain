# MontAI: first public academic testnet deployment

This is a manual, free-tier **Sepolia test** release, not a production/mainnet launch. No deployment transaction is authorized by this document. Keep the current localhost configuration and demo data intact. Never send credentials, seed phrases, or master keys in chat, Git, PRs, screenshots, or logs.

## Release checklist

1. Review the deployment PR and its tests; merge only after team approval. Record the release commit. Do not automatically merge or rewrite branches.
2. Create a dedicated Sepolia deployer wallet privately. Never use a Hardhat fixture account or share its seed. The deployer is the platform recipient under the existing contract; use distinct creator and buyer wallets.
3. Obtain a small amount of **free Sepolia ETH**. Use the [Ethereum Sepolia faucet directory](https://ethereum.org/developers/docs/networks/#sepolia). Faucet eligibility varies; do not buy mainnet ETH to qualify. Test tokens have no monetary value. Allow gas as well as the test purchase price.
4. Configure Alchemy Free Ethereum Sepolia RPC. Keep the deployment/backend RPC credentials server-side. The browser's separate `VITE_RPC_URL` is public: restrict its app with an appropriate domain allowlist. A browser-origin-restricted key may not work from the backend. Never enable paid plans for this test.
5. Configure the existing Pinata server-side JWT with **V3 Files WRITE**. Uploads use `POST https://uploads.pinata.cloud/v3/files`, not legacy pinning endpoints. Only AES-GCM ciphertext is uploaded. Confirm the configured HTTPS IPFS gateway can retrieve its public ciphertext CID. No raw model or decryption key belongs on IPFS.
6. Create `montai-private-records` in Supabase Storage with **Public OFF**. Inspect existing `storage.objects` policies: no anonymous or ordinary authenticated user may SELECT/INSERT/UPDATE/DELETE this bucket. A private flag alone does not override permissive RLS policies. Test anonymous and ordinary-user reads against a known object: both must be denied. Never add public-read policies or expose signed URLs for these records. Service-role access is backend-only; it bypasses RLS.
7. Generate a fresh 32-byte production master key privately (64 hex characters) and store it in your secure credential manager and Render environment. Do not reuse the localhost key. Preserve this **exact same key** across restarts, redeploys and rollbacks. Losing/changing it makes previously wrapped file keys unusable. Store an independent secure backup; do not print the existing key or commit it.
8. Privately provide `SEPOLIA_RPC_URL` and `SEPOLIA_PRIVATE_KEY` to the root Hardhat process, then run `MONTAI_DEPLOY_DRY_RUN=1 npx hardhat run scripts/deploy.ts --network sepolia`. `.env` is not automatically loaded by Hardhat; supply variables securely through your environment or Node's env-file support. The script rejects known Hardhat public keys and networks other than localhost/Sepolia. Dry run does not deploy.
9. Obtain explicit human approval for the actual testnet transaction. Only then run `MONTAI_ALLOW_TESTNET_DEPLOYMENT=sepolia npx hardhat run scripts/deploy.ts --network sepolia` with the same private environment. Do not run on mainnet. Stop on insufficient test ETH or configuration errors; never auto-retry a wallet transaction.
10. Record the receipt transaction hash, contract address and deployment block from Sepolia. Confirm chain `11155111`, receipt success, deployed bytecode and platform/deployer address. Retain them in your release notes; do not reuse a localhost address merely because the hex string looks familiar.
11. Create a Render **Free** Node web service: repository root directory `backend`, build command `npm ci`, start command `npm start`, health path `/health`. Configure Node 22 with `NODE_VERSION=22`; host `0.0.0.0`. Use Render's injected `PORT`, not a hard-coded local port. No persistent paid disk is required.
12. Privately set Render variables from `backend/.env.production.example`: `NODE_ENV=production`, `RPC_URL`, `CHAIN_ID=11155111`, `CONTRACT_ADDRESS`, exact canonical HTTPS `CLIENT_ORIGIN`, `MODEL_MASTER_KEY`, `PINATA_JWT`, `IPFS_GATEWAY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_RECORD_BUCKET`, `HOST=0.0.0.0`. Reserve the Vercel project/domain first so this origin is known. Do not copy secrets into frontend settings.
13. Start the backend. Missing required values, wrong chain, absent contract or a non-private bucket must fail startup. `/health` must return only status, chain ID and contract address. Verify `11155111` and the new address. It checks contract access, not a complete Pinata/Supabase write/read acceptance test.
14. Create a Vercel **Hobby** project with root `frontend`, install `npm ci`, build `npm run build`, output `dist`, Node 22. Configure only public `VITE_RPC_URL`, `VITE_CHAIN_ID=11155111`, `VITE_CONTRACT_ADDRESS`, `VITE_DEPLOYMENT_BLOCK` (actual deployment block), `VITE_API_URL` (HTTPS Render origin), and optional profile `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`. Every `VITE_*` value is browser-visible. The build rejects known server-secret names, service-role JWTs and copied server credentials; this is an extra guard, not permission to enter secrets.
15. If using existing Supabase profiles, set Auth Site URL to the exact canonical HTTPS Vercel origin. Allow exact `/profile` and `/login` redirects used by the app; retain localhost redirects only if needed for development. Verify the existing Google provider and its Supabase callback separately. Do not weaken profile RLS or confuse profile identity with wallet licensing.
16. Deploy the frontend manually and verify deep links `/marketplace`, `/dashboard`, `/upload`, `/activity` and a real `/model/<id>` (the SPA rewrite is in `frontend/vercel.json`). Check HTTPS, exact backend CORS origin, no secrets in bundles, and no reliance on an arbitrary preview origin.
17. Connect MetaMask on Sepolia. Verify network name and wrong-network handling; missing Sepolia invokes switch-then-add only after error 4902, with HTTPS RPC and real Etherscan URLs. Rejecting a prompt must not cause retries. Authenticate by the existing nonce/signature challenge; account/network changes must clear stale session and license state.
18. Register one small non-sensitive test model through the real creator flow. Record original SHA-256, ciphertext CID, mined registration transaction and model ID. Confirm Marketplace/Details match chain state. Inspect private record metadata without printing wrapped keys: object path is `11155111/<lowercase-contract-address>/<cid>.json`. It includes hashes, owner, model metadata and the wrapped file key, never the raw model or master key.
19. With a separate buyer wallet, freshly verify `hasLicense=false`, purchase with test ETH using MetaMask, wait for receipt success, then freshly verify `hasLicense=true`. Record the transaction and check License Owned. Creator revenue accrual and withdrawal remain the existing contract behavior; no token or royalty redesign.
20. Authenticate a distinct unlicensed wallet and confirm protected download returns 403. Backend must independently check the on-chain license/owner; UI or Supabase profile state is not authorization. Switch creator/buyer/unlicensed wallets and verify stale access does not survive.
21. Download as the licensed buyer and verify decrypted SHA-256 equals the chain hash and original file. Restart/redeploy Render so its local ciphertext cache is absent, keep the same master key and private bucket, re-authenticate, and repeat download. The backend must fetch the private wrapped record and verify/decrypt IPFS ciphertext successfully. Record this **live persistence acceptance test**; mocked tests alone do not prove provider configuration works.
22. Review real Activity/provenance events and authentic Sepolia explorer links. Free Alchemy queries are paginated in **10-block** ranges, with Load older blocks and a deployment-block floor. The feed is not a full-history indexer: older events require pagination and may be slow over long periods. Empty loaded ranges are not proof of no historical events. Record public URLs and test receipts, not secrets.

## Persistence and security boundaries

Local development without Supabase keeps protected JSON/files in its existing filesystem namespace. Production requires both Pinata and the private persistent store and **never falls back to filesystem key records**. Supabase writes do not overwrite objects. A remote failure stops the upload/download rather than returning a fake success. Cached ciphertext is disposable; wrapped records and the stable master key are not. Storage requests are bounded, authenticated, reject redirects, and check the private bucket at startup and on each operation.

Render Free may sleep and uses an ephemeral filesystem. The frontend shows a delayed access-service wake-up message, waits up to 90 seconds, and does not automatically retry transactions or keep the server artificially awake. Sessions/challenges are intentionally in memory: a restart requires a fresh wallet signature, not re-purchasing a license. Current conservative API rate limits may be shared by clients behind Render's proxy; never blindly trust forwarded headers to bypass them. A 429 requires waiting and re-authenticating if necessary, not automatic loops.

## Redeploy and rollback

Keep the same chain, contract address, bucket, namespace and master key to retain existing models/licenses. Frontend environment changes require a new build; backend variable changes require restart. Roll back to a reviewed compatible commit without deleting records or force-pushing. Returning to a version without persistent record support is **not** a safe production rollback. A new contract is a distinct registry/namespace: old licenses and models do not migrate automatically. Preserve old addresses, records and key backups; do not rotate the master key casually. Pause release if persistence or negative authorization checks fail.
