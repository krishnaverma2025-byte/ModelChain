# Combined public-demo stability batch

This branch is a single reviewed release batch. **Do not merge, deploy, or change production settings until the user approves the whole batch.** No Solidity changes or contract redeployment are required.

## Root causes and changes

1. **Reload authentication:** the wallet session was memory-only. `sessionStorage` now holds only the opaque bearer header, wallet address, chain ID and expiry. Reload is unauthenticated while provider account/chain, optional linked profile, backend session/deployment and expiry are verified. Backend rejection, expiry, real wallet/network change, disconnect, logout or profile mismatch clears the stored hint. Server restarts still invalidate in-memory backend sessions and require a new signature. Storage blocked by the browser degrades to memory-only auth. Session storage is not an authorization source and remains sensitive to same-origin XSS; signatures/challenges/keys are never persisted.
2. **Redundant events:** every account/network notification previously revoked auth, even when values matched. Canonical account/chain comparisons now preserve identical notifications; real changes immediately invalidate auth and cancel stale login attempts. Details no longer separately clears license state on duplicate notifications. Backend verification and pre-transaction wallet checks remain mandatory.
3. **Orphaned uploads:** encrypted storage precedes registration, with no compensation. New private records optionally include `pinataFileId` from the V3 upload response. `DELETE /api/uploads/:cid` requires a wallet session, upload ownership, valid CID, a bounded authoritative registry scan (including inactive registrations) and an unchanged model count. Any registered CID is denied. RPC failures fail closed; registries over 500 models require manual review. Pinata deletion uses `DELETE https://api.pinata.cloud/v3/files/public/<id>`, then private Supabase deletion and ephemeral-cache removal. No credentials/file keys/Pinata file ID are returned to the browser.
   - Explicit rejection or failure before submission, or a known reverted receipt: one compensating attempt.
   - Successful receipt, known broadcast hash with unknown result, or ambiguous network/timeout error during submission: retain upload; do not retry/send/delete automatically.
   - The frontend blocks resubmission after an ambiguous no-hash RPC failure while that page remains mounted. Check wallet history manually before proceeding.
   - After any compensation attempt, its CID is never reused by the form: even a reported cleanup failure may already have unpinned ciphertext. A later explicit retry uploads a fresh encrypted package; remnants require operator review.
   - Cross-service atomicity is impossible. The chain scan cannot lock Ethereum against a concurrent registration. Cleanup is intended only for abandoned uploads, never as an asset-management/delete feature. IPFS unpinning cannot erase copies retained by other peers. Reload/unmount or failed/expired auth may leave an orphan requiring manual operator review; there is no background deletion job.
4. **Request storms:** a single 60/minute API budget coupled all operations; remounts repeated reads. Endpoint-specific per-socket-IP limits now isolate challenge (30/min), session creation (30), verification (120), logout (30), uploads (10), cleanup (10), downloads (40), and public metadata (240). Health has no normal API quota. Responses are clean JSON 429 with retry guidance; no automatic retry. Identical in-flight catalog/metadata/session/contract/event reads share work; stale metadata/catalog consumers cancel without cancelling other consumers. Reads are not cached as durable auth/license state. Render forwarding headers remain untrusted; users may share conservative category quotas behind its proxy. Limits are per process, suitable for the current single-instance demo, not a distributed abuse-control system.
5. **Mobile handoff:** provider absence previously offered only extension guidance. Mobile browsers without injection get an explicit **Open MontAI in MetaMask** link, never an automatic redirect. Safe public HTTPS origins retain the current path; query/fragment state is deliberately dropped. Unsafe/local origins fall back to the canonical public MontAI URL. Desktop guidance and injected-wallet flows remain intact. Installed-app/browser/OS universal-link handling must still be checked on physical iOS/Android devices.

## Compatibility and configuration

- No new environment variables. Do not change the deployed contract, chain, deployment block, master key, bucket, origins or existing credentials for this batch.
- Existing protected records without `pinataFileId` remain readable/downloadable. Their cleanup is denied for manual review rather than guessing a Pinata ID. No bulk migration or backfill.
- The existing server-side Pinata credential must permit the V3 file-delete operation. A denied delete fails safely without deleting the protected record. An operator must verify applicable permissions after approval; this branch does not change keys/permissions. Supabase server-side Storage deletion must also work against the existing private namespace. Policies are not weakened.
- Upload persistence failure makes one best-effort Pinata compensation before any CID is returned. If the storage write outcome was ambiguous, protected records are retained for manual review rather than risking unrelated deletion.
- The session verification response adds `expiresAt`, `chainId`, and `contractAddress`. Deploy the backend before the matching frontend; an older backend fails reload restoration safely and requires fresh sign-in.

## Exact post-approval release procedure

1. Review this consolidated PR, green CI and all five fixes together. Obtain explicit user approval to merge/deploy. No partial release.
2. Check whether Render/Vercel auto-deploy on `main`. Arrange an operator-controlled release window so merging does not publish one half without verification. Do not change those settings before approval.
3. Merge the approved PR without force-pushing. Record both previous service deployments and the approved commit for rollback.
4. Deploy the **backend first** from that commit on the existing Render service, with the same environment. Check `https://montai-api.onrender.com/health`: chain `11155111`, contract `0x50Af9D424C10D596ddb5f5cF9A18Fc193a73e97e`. Verify authenticated session GET adds correct public deployment fields and expiry. Confirm private bucket and server-only credentials remain unchanged.
5. Deploy the **frontend** from the same commit on the existing Vercel project, without environment changes. Keep chain `11155111`, that contract, deployment block `11907790`, API `https://montai-api.onrender.com`, and origin `https://montai-six.vercel.app`. Check direct route refreshes.
6. With real MetaMask, verify reload restoration without a new signature, duplicate notifications and all four successful transaction types preserving auth; account/network changes, logout/disconnect and profile mismatch clearing auth. Backend restart should require sign-in again, not repurchase.
7. Upload one small non-sensitive fixture and reject registration before broadcast. Confirm one authenticated cleanup and no private record/cache left, using only that fixture's new Pinata file ID. Confirm successful and already-registered models cannot be cleaned up. Do not delete existing user/demo models to test this. Verify an unknown/pending broadcast is retained. Confirm safe reporting if cleanup permissions are unavailable.
8. Verify normal browsing, 429 feedback without retries, fresh licenses, independent backend authorization, an unlicensed denial and licensed SHA-256-verified download. Check mobile CTA/no redirect on real iOS/Android, desktop extension guidance and injected mobile wallet flow.
9. If acceptance fails, stop the release and roll back **both** services to their reviewed compatible previous versions. Keep the same master key and private records. Never delete keys/data to repair a release or roll back Solidity.
